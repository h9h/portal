# Portal

Portal is a framework for building a web application, that supports context dependent views. Those views come from a microservice/self contained system architecture.

Portal delivers a few common capabilities:
- Login via a configurable set of OAuth 2 authorization servers, selected explicitly by the user (e.g. a "Sign in with GitHub" button). GitHub is the first supported provider; more can be added later without changing this model. Portal does not own user credentials — that stays with the chosen provider.
- Registration workflow: on a user's first successful login via a provider, Portal provisions a local profile for that identity and assigns initial role(s). There is no separate sign-up form and no Portal-owned password.
- Rights management
- all routes are secured and checked against the rights of the authenticated user
- rights are managed via roles
- navigation menu, dependent on rights and context

## Architecture

Portal is a backend-for-frontend paired with a client shell: a single-page application that Portal serves once per browser session and that then mounts SCS-contributed components into itself as the user navigates, without full page reloads. Portal's server owns the OAuth2 login flow, route security, the nav menu, and proxying every request an SCS needs to see; the client shell owns the persistent page chrome, client-side routing, and a small runtime shared by every mounted component. Each SCS owns its own domain logic, its own rights, the client-side component(s) it contributes, and the fragments/data those components fetch.

### Request flow

Portal serves two fundamentally different things over `GET`, distinguished by whether the request carries the client shell's data-marker header (`X-Portal-Data: 1`, attached by every call the `@portal/runtime` fetch helper makes — see Client shell below). Portal's own fixed routes (`/health`, `/auth/*`, `/me`, `/nav`, `/admin/*`, `/_scs/*`, `/_shell/*`, `/routes`) always take precedence over both flows below, checked by exact `pathname` equality (not the trailing-slash-normalized matching the data-fetch flow uses below) — an SCS attempting to claim one of these paths is silently shadowed rather than reported as a collision. This precedence is exact-path only, so e.g. `/admin/users/` (trailing slash) does not match Portal's own `/admin/users` handler and can fall through to an SCS-declared route at that normalized path instead; the consequence is bounded, since the SCS is already operator-configured and trusted.

**Page navigation** (no data-marker header): every such request, for any path, in any auth state, returns the same client shell bootstrap HTML — Portal doesn't consult the route index or check authentication for these at all. The shell is a static, unauthenticated document; once loaded it fetches `/me` and `/routes` itself, and its client-side router decides what to actually render (a login prompt, a 404, or the resolved view). This is a deliberate change from an earlier version of this spec, where an unauthenticated request to an enforceable path returned 401 before reaching any handler — that guarantee now applies only to the data-fetch flow below; a page load itself is never gated at the HTTP level, only the real data a mounted component subsequently fetches is.

**Data fetch** (data-marker header present): this is the original composition model, unchanged in mechanics. Portal checks the target route's required role(s), from the relevant SCS's manifest, against the authenticated user's role assignments — an unauthenticated caller gets 401, an authenticated caller lacking the role gets a generic 403 with no `requiredRoles` (Portal logs the required roles server-side for diagnostics but doesn't reveal them to an unauthorized caller), both before Portal ever contacts the SCS, so an unauthenticated caller can't distinguish "no route declares this path" from "a route declares this path but you're not logged in." If authorized, Portal calls the SCS server-side (attaching a signed internal token — see below) and forwards its response back as Portal's own response, unmodified beyond forwarding the content-type; Portal never interprets the payload. Each manifest route still maps to exactly one SCS and one exact path — a mounted component that needs several distinct pieces of data from its own SCS declares a separate `routes` entry (with whatever role each actually requires, which may differ from the role required to view the page that mounts the component) for each one. True multi-component composition on a single page — several SCSs' components mounted into the same page simultaneously — remains deferred; this stage still mounts exactly one component (the current route's) into a single content region. Only `GET` is enforced/composed this way; the manifest schema has no HTTP method field yet, so mutations a mounted component might want to make aren't handled by this mechanism. Before checking the route index, Portal normalizes the incoming request path by stripping any trailing slashes (so `/orders`, `/orders/`, and `/orders///` all match the same declared route; `/` itself is left as-is); the query string is not part of route matching (though it's still forwarded to the SCS as part of the request). The fetch to the SCS never follows redirects — a redirect response from an SCS is treated as a failure (502), since this flow only ever returns that one SCS's own response, never content from wherever it might redirect to.

### SCS manifest contract

Each SCS exposes a manifest endpoint (`GET /.portal/manifest`) that Portal fetches at startup and periodically thereafter. The manifest declares, for that SCS:
- `name`: the SCS's identity, used for role namespacing (e.g. `orders` → roles like `orders:admin`)
- `bundle`: the path (relative to the SCS's own base URL) to its client-side component bundle — a JS module exposing one export per mountable component (e.g. `/.portal/bundle.js`)
- `routes`: the routes/fragments it serves, each with its required role(s) and, when the route is meant to be mounted as a page (as opposed to a pure data endpoint), the `component` export from `bundle` to mount for it
- `nav`: the nav menu entries it contributes, each with its required role(s)
- `publishesContext`: the shared-context keys (see Shared context below) this SCS is the sole writer of
- `consumesContext`: the shared-context keys this SCS's components read — declared for documentation and collision-tracking, not access control

```json
{
  "name": "orders",
  "bundle": "/.portal/bundle.js",
  "routes": [
    { "path": "/orders", "requiredRoles": ["orders:viewer"], "component": "OrdersView" },
    { "path": "/orders/summary", "requiredRoles": ["orders:viewer"] }
  ],
  "nav": [{ "label": "Orders", "path": "/orders", "requiredRoles": ["orders:viewer"] }],
  "publishesContext": [],
  "consumesContext": ["profile"]
}
```

Portal has no built-in knowledge of any SCS's routes, nav entries, roles, components, or context keys beyond what the manifest declares — adding a new SCS means registering its manifest, not changing Portal's code. A route without a `component` field is a pure data endpoint (like `/orders/summary` above) — it's fetched by an already-mounted component's own code, and is never itself mounted as a page. A nav entry's domain/context (see Context model below) is the owning SCS's own `name` — one SCS, one domain, for this stage; an SCS contributing to multiple domains is future scope if it turns out to be needed.

**Discovery**: Portal is configured with a static list of known SCS base URLs (e.g. `PORTAL_SCS_URLS`, comma-separated); it appends `/.portal/manifest` to each to fetch. Adding an SCS means adding it to this list, not building a self-registration mechanism (deferred as unnecessary complexity for this stage).

**Fetch and failure handling**: Portal fetches every configured SCS's manifest at startup and on a fixed refresh interval thereafter. A malformed response is treated the same as an unreachable SCS: Portal logs the failure, keeps serving the last-known-good manifest it has for that SCS (or nothing, if it has never successfully fetched one), and marks that SCS's data as stale. A transient failure in one SCS doesn't remove its routes or nav entries from users mid-session. This applies uniformly to the new fields too — a manifest with, say, a route naming a nonexistent `component` or a malformed `publishesContext` is rejected as a whole (same as any other malformed manifest), not partially accepted.

### Client shell

Portal serves a single client shell: a small React application, bootstrapped once per browser session by the static HTML page returned for every page-navigation request (see Request flow above), that stays mounted for the life of the session and swaps its content region as the user navigates, without full page reloads.

**Bootstrap**: on load, the shell fetches `/me` (identity and roles) and `/routes` (a flattened view of the route index Portal already builds server-side — path, owning SCS, required roles, and `component` name where present) to build its client-side router. `/routes` requires authentication (401 if not logged in), same as `/me` and `/nav` — this preserves the existing "an anonymous caller can't enumerate which paths exist" invariant even though the page HTML itself is now served unauthenticated; an anonymous visitor's shell gets a generic login prompt with no per-path detail until they log in. Unlike `/nav`, once authenticated, `/routes` is not role-filtered — the client needs to know a path exists and what role it needs in order to render a "you don't have access" state rather than a blank 404 for a route the current user can't reach; the underlying data stays protected by the data-fetch flow's server-side check regardless of what the client believes.

**Resolving and mounting a route**: the client-side router matches the current path against `/routes`' table using the same exact-path matching Portal's server-side route index uses (parameterized/prefix routes remain deferred, same as server-side). Once resolved to an SCS + `component`, the shell `import()`s that SCS's bundle from `GET /_scs/<scsName>/bundle.js` — a Portal-proxied endpoint, authentication-required but not role-gated (the bundle contains only component code, no user data; the role check happens on whatever data endpoints the mounted component itself subsequently calls), failing the same way as any other unreachable-SCS fetch (502) — and mounts `module[component]` into its content region, wrapped in a React error boundary local to that region, so a broken or missing export shows a local error state instead of taking down the whole shell.

**Sharing one React instance across independently-built bundles**: the shell's bootstrap HTML declares an import map resolving the bare specifiers `"react"`, `"react-dom"`, and `"@portal/runtime"` to URLs under `/_shell/*` — Portal's own first-party static assets, served publicly with no authentication check at all (unlike `/_scs/*`), since they include the shell app itself and must be fetchable before login just to render a login screen. Every SCS's bundle is built treating these as externals rather than bundling its own copies, so every mounted component — regardless of which SCS built it — shares the exact same React instance, ReactDOM instance, and shared-context store as the shell and every other mounted component. `@portal/runtime` is the module SCS component code actually imports; it exposes the shared-context hooks (see Shared context below) and the fetch helper that attaches the `X-Portal-Data: 1` marker header so data calls are routed correctly by the request flow above.

**Data endpoints**: a mounted component fetches its own data by calling whatever paths its own manifest declared under `routes` (with or without a `component`) via the `@portal/runtime` fetch helper — this reuses the existing composition/proxy mechanism unchanged, just marked as a data request rather than a page navigation.

**Client-side navigation**: `@portal/runtime` exposes `usePortalNavigate()`, returning a function a mounted component calls explicitly (e.g. from a link's click handler) to move to a new path without a full page reload — it updates the browser's history (so back/forward work) and the shell re-resolves and re-mounts for the new path. This stage does not automatically intercept ordinary `<a>` clicks (that requires deciding same-origin/modifier-key/target edge cases, deferred); a component that wants a real `<a>` to navigate client-side calls `usePortalNavigate()` from its own click handler.

**Open gap, deliberately deferred**: this stage does not wire the shell up to actually obtain or hold a browser-facing access token, so as implemented the shell can only ever reach the "please log in" state — `@portal/runtime`'s `portalFetch` never attaches an `Authorization` header, nothing client-side stores a token, and `GET /auth/callback/:provider` (from an earlier stage of this spec, predating the client shell) still returns the token pair as a JSON body to whatever navigated there, which under this stage's request-flow split is a real browser navigation, not a call the shell's own code can intercept and read. Closing this gap means deciding, as its own piece of design work: where the token lives client-side (in-memory only vs. `sessionStorage` vs. something else, weighed against XSS exposure), and how the OAuth callback hands the token to the already-running shell rather than rendering raw JSON in its place — a real design question, not a small fix, and out of scope for this stage. Until it's closed, the shell is honest about its own state (a login prompt, not a crash or a misleading "logged in" flicker) but cannot progress past it in a real browser.

### Shared context

Distinct from the Context model below (which is about which domain/entity is currently active), shared context is a small cross-SCS data-exchange mechanism: any mounted component can publish keyed values that any other mounted component — from any SCS — can read and re-render on change, so one SCS's component (e.g. a `profile` SCS publishing the user's display name and avatar) can be consumed by another SCS's component (e.g. a `contactData` SCS wanting to show that same name next to an address) without either SCS knowing about the other's routes, roles, or manifest.

**Ownership**: each shared-context key is declared, up front, in exactly one SCS's manifest `publishesContext` list. Portal validates ownership the same way it validates route ownership: when building the route index from the manifest registry snapshot, it also builds a context-ownership index, keyed by context key. If two different SCSs (by configured base URL, the same "different SCS" rule route collisions use) both declare the same `publishesContext` key, that key is excluded from the valid set entirely for as long as the collision persists, and it's logged the same way a route collision is — no last-writer-wins, no merge. `consumesContext` is documentation and collision-tracking only, not an access-control gate — any mounted component can subscribe to any valid published key, whether or not its own SCS declared it as consumed.

**Storage and lifecycle**: shared context lives entirely in the browser, in the shell's long-lived module scope — it is never sent to or stored by Portal's server, and has no relationship to the browser-facing access token or the internal SCS token. It survives client-side navigation (a value published by a component that has since unmounted is still readable by whatever mounts next) but not a full page reload — context is rebuilt from scratch as components remount and republish. Cross-tab synchronization and any form of persistence are explicitly out of scope for this stage.

**Runtime API** (`@portal/runtime`): `usePublishedContext(key)` subscribes the calling component to a key's current value (`undefined` if nothing has published to it yet), built on React's `useSyncExternalStore` so it works correctly regardless of how many separate mount roots exist. `usePublishContext(key)` returns a setter, but only functions for a key the calling SCS actually declared in its own `publishesContext` — the shell knows which SCS a mounted component belongs to (it did the `import()`), so a call for a key that SCS didn't declare (or that's currently collision-voided) is a no-op with a `console.warn`, never a thrown exception; a misconfigured SCS's context calls can't crash another SCS's mounted component, the same design goal a route collision already serves for routing.

### Identity, sessions, and rights

- **Login**: user explicitly picks a provider (e.g. "Sign in with GitHub") from Portal's configured list of OAuth2 authorization servers. Portal acts as the OAuth2 client; it never sees or stores the provider's password.
- **Redirect URI**: the OAuth `redirect_uri` sent to the provider defaults to the incoming request's own origin, which is only correct for local/plain-HTTP development. In any deployment behind TLS or a reverse proxy, Portal's base URL must be configured explicitly (`PORTAL_BASE_URL`, or the `baseUrl` server option) so the registered callback matches what's actually sent — otherwise the provider will reject the exchange with a redirect URI mismatch.
- **First login**: Portal provisions a local profile linked to the provider identity, with no roles assigned by default.
- **Browser ↔ Portal**: after login, Portal issues its own bearer token (not the provider's token). The frontend stores it and sends it as `Authorization: Bearer …` on requests to Portal. Logout discards/invalidates this token; it is short-lived and reissued via a refresh flow rather than long-lived.
- **Portal → SCS**: for each request that needs an SCS fragment, Portal mints a short-lived signed internal token (JWT) carrying the user id, the user's roles for that SCS, and the target SCS's base URL as an audience claim. The SCS verifies the signature; it does not need to know how the user originally authenticated. The internal token is signed with its own secret (`INTERNAL_TOKEN_SECRET`), separate from the browser-facing access token's secret — they protect different trust boundaries (browser-facing vs. backend-service-facing), so a leak of one must not compromise the other. Its roles claim is filtered to only the target SCS's namespaced roles (e.g. calling the `orders` SCS includes only that user's `orders:*` roles) — an SCS never learns a user's roles in unrelated SCSs. The audience claim exists so a real SCS implementation can reject a token that was minted for a different SCS and replayed against it; Portal itself doesn't need to check its own audience claim, since it's the issuer, not a recipient.
  - **Open question, deliberately deferred**: role-namespace filtering is currently keyed on the SCS manifest's self-declared `name` field — the same field the Route collisions rule above (correctly) treats as untrustworthy-as-identity for collision purposes. A compromised or misconfigured first-party SCS could self-declare a `name` matching another SCS's namespace and receive a token carrying that namespace's roles, which the audience claim only partially defends against (it stops replay against the *real* SCS of that name, but doesn't stop the *misdeclaring* SCS from being handed the token in the first place). Closing this fully means deriving the role namespace from a Portal-side mapping (e.g. keyed on base URL) rather than the manifest's own `name` field — a larger change than this stage makes, and explicitly left as a future decision. The existing trust model (SCS base URLs are static, operator-configured, never self-registered) bounds the risk to an already-trusted-but-compromised or misconfigured SCS, not an external attacker.
- **Roles**: namespaced per SCS (e.g. `orders:admin`, `billing:viewer`), defined by each SCS via its manifest — no cross-SCS collisions, no central coordination of role names. Portal stores user→role assignments (a flat set of namespaced role strings per user); it does not define what a role means, that's the owning SCS's responsibility.
  - **Admin authority**: a single reserved, non-namespaced role, `portal:admin`, grants full authority to assign or revoke any role (SCS-namespaced or not) to or from any user via the admin API below. There is no per-SCS delegated admin authority in this stage — an SCS cannot grant its own `orders:admin`-style roles without going through a `portal:admin`.
  - **Bootstrap**: since granting a role requires an existing `portal:admin`, and nothing grants one automatically otherwise, Portal is configured with a static list of admin emails (`PORTAL_ADMIN_EMAILS`, comma-separated). On every successful login, if the authenticated user's email matches, Portal ensures they hold `portal:admin` (granting it if missing — idempotent, safe to repeat every login). This is self-healing in one direction only: if `portal:admin` is ever accidentally revoked from a listed user, the next login by that email restores it — but removing an email from the list does NOT revoke `portal:admin` from a user who already holds it; the list only ever grants, it is not treated as an authoritative membership set. There is no guard against an admin revoking their own or the last remaining `portal:admin` — the bootstrap list is what prevents a true lockout, not an in-app safeguard.
    - **Trust assumption**: this bootstrap trusts the OAuth provider's reported email as-is, with no `email_verified` check and no binding to which provider reported it. This is safe with GitHub as the sole provider today, since GitHub's public-profile email can only be an address already verified on that account — but it is not safe in general. A provider whose `email` claim is user-settable and unverified (common in plain OIDC) would let anyone who can make that provider report a listed address obtain full role-assignment authority. Adding a second provider must revisit this assumption before relying on `PORTAL_ADMIN_EMAILS` for it; provider-scoping the list (e.g. `github:admin@example.com`) is the likely fix, not yet implemented.
  - **Admin API**: `GET /admin/users` (list every user with their id, email, display name, provider, and current roles), `POST /admin/users/:userId/roles` with body `{ "role": string }` (assign a role, returns the user's updated role list), `POST /admin/users/:userId/roles/revoke` with body `{ "role": string }` (revoke a role, same response shape) — all three require the caller to hold `portal:admin` (401 if unauthenticated, 403 if authenticated but not an admin) and 404 if `:userId` doesn't exist. These follow the same POST-for-mutation convention as the rest of Portal's API (no `DELETE` verb is used anywhere in this codebase). `portal:admin` is Portal-only — an SCS manifest's `requiredRoles` is not meant to reference it, and Portal never includes `portal:admin` in the roles claim of the internal token it mints for an SCS, regardless of what that SCS calls itself.
- **Route enforcement**: always performed by Portal, before any SCS is called for data, using the manifest's declared required role(s) for the route. The one exception is the bundle endpoint (`GET /_scs/<scsName>/bundle.js`, see Client shell above), which requires authentication but performs no role check — a bundle carries only component code, never user data, so the role boundary is enforced entirely at the data-fetch layer instead.
  - **Route index**: built from the manifest registry's current snapshot, indexing every declared route path across all SCSs that have a manifest (using the last-known-good manifest even if that SCS is currently marked stale — the routes it last declared are still enforceable). Matching is exact-path only for this stage; parameterized/prefix routes are future scope.
  - **Route collisions**: if two different SCSs declare the same route path, that path is excluded from the enforceable index (requests to it resolve as not-found) and the collision is reported separately so it can be logged or alerted on — a route path belongs to exactly one SCS by design, so a collision is a configuration error, never silently resolved by picking a winner. "Different SCS" is judged by configured base URL, not by the manifest's self-declared `name` — a manifest's `name` is content Portal fetched from that endpoint, not something Portal can trust as an identity, so two distinct configured base URLs are always treated as different SCSs for collision purposes even if their manifests happen to declare the same `name`.
  - **Empty `requiredRoles`**: a route declaring `"requiredRoles": []` is public — any authenticated user may access it. This check happens only for requests that have already passed authentication; the access check itself has no notion of an anonymous caller.
  - **Access check outcomes**: for a given request path and the user's roles, the result is one of: allowed (the route matches and the user holds a required role, or `requiredRoles` is empty); not-found (no route declares this exact path); or forbidden (the route matches but the user holds none of its required roles). Path matching is exact-string — normalizing a request path (trailing slashes, case, query strings) before this check is the caller's responsibility, not something the check itself does.

### Context model

This is unrelated to Shared context above, which is about cross-SCS data exchange between mounted components, not which domain is active — the name collision is unfortunate but both terms were already established when Shared context was added, so this note exists instead of a rename. Context = the current SCS/domain (required), with an optional selected entity (e.g. a workspace or project) nested inside it. There is no tenant/organization concept — multi-tenancy was explicitly considered and deferred; Portal is single-tenant for now. The nav menu is the union of nav entries from every registered SCS's manifest, filtered to the entries whose required role the current user holds, and further scoped to the current domain/entity.

**This stage's nav model**: domain/entity scoping is deferred — there is no session-level concept yet of a "current domain" to scope against, so `GET /nav` (authenticated the same way as `/me`) returns the full role-filtered union of nav entries across every configured SCS, each tagged with the owning SCS's `name` as its `domain` (`{ label, path, domain }`). Filtering reuses the same manifest-snapshot-plus-role-check logic as route enforcement (an entry with empty `requiredRoles` is visible to any authenticated user; entries from a stale-but-previously-successful SCS remain visible, same as for routes), but nav entries are never collision-checked against each other the way routes are — nav is purely a list of links to show, not something Portal enforces access through, so two SCSs contributing a nav entry for the same path is harmless. Because duplicate `path`s across SCSs are legal in nav (unlike routes), `path` alone is not a stable identity for a returned entry — a frontend should key on `domain` + `path` together. One consequence of routes being collision-checked while nav isn't: if two SCSs collide on a route path, that path is removed from the enforceable route index (so visiting it 404s) while both SCSs' nav entries for it are still listed — `/nav` can durably advertise a dead link in that already-misconfigured (and already-logged) situation.

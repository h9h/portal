# Admin API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Portal a way to assign and revoke roles over HTTP, gated by a new reserved `portal:admin` role, with an email-based bootstrap mechanism so the very first admin can be granted without already having one.

**Architecture:** Two small additions to the already-reviewed `src/auth/users.ts` (`listUsers`, `findUserById`). Then two `src/server.ts` changes: (1) on every successful OAuth login, grant `portal:admin` to a user whose email matches a configured allowlist (self-healing, idempotent); (2) three new authenticated, `portal:admin`-gated endpoints — `GET /admin/users`, `POST /admin/users/:userId/roles`, `POST /admin/users/:userId/roles/revoke` — built on the existing `assignRole`/`revokeRole`/`getUserRoles` in `src/rights/roles.ts`.

**Tech Stack:** Bun runtime + `bun:test`, `bun:sqlite`, TypeScript. No new dependencies.

**Spec:** `specification.md` (Architecture → Identity, sessions, and rights → Roles → Admin authority, Bootstrap, Admin API)

## Global Constraints

- Runtime and bundler is bun; TypeScript for frontend and backend-for-frontend. (`Claude.md`)
- Minimize external dependencies — ask before introducing a new one. (`Claude.md`, `specification.md`)
- Every feature needs a set of test cases, run via `bun:test`, files under `./__tests__`. (`Claude.md`)
- `portal:admin` is a single reserved, non-namespaced role with full authority to assign/revoke any role to/from any user; there is no per-SCS delegated admin authority. (`specification.md`)
- Bootstrap: `PORTAL_ADMIN_EMAILS` (comma-separated) is checked on every successful login; a matching email gets `portal:admin` granted (idempotent, self-healing). (`specification.md`)
- All three admin endpoints require `portal:admin`: 401 if unauthenticated, 403 if authenticated but not an admin, 404 if the target `:userId` doesn't exist. (`specification.md`)
- No guard against revoking the last/one's-own `portal:admin` — the bootstrap list is what prevents a true lockout. (`specification.md`)
- Endpoints follow the existing POST-for-mutation convention (no `DELETE` verb anywhere in this codebase): `POST /admin/users/:userId/roles` to assign, `POST /admin/users/:userId/roles/revoke` to revoke, both with body `{ "role": string }`. (`specification.md`)
- Portal's own fixed routes (now including `/admin/*`) always take precedence over an SCS-declared route of the same path — place new route checks before the generic SCS-composition catch-all, matching the existing pattern for `/health`, `/me`, `/nav`. (`specification.md`, existing `src/server.ts` structure)

export function findUserById(db: Database, id: string): User | null {
  return db
    .query(
      `SELECT id, provider, provider_user_id as providerUserId, email, display_name as displayName
       FROM users WHERE id = ?`
    )
    .get(id) as User | null;
}

export function listUsers(db: Database): User[] {
  return db
    .query(
      `SELECT id, provider, provider_user_id as providerUserId, email, display_name as displayName
       FROM users ORDER BY created_at`
    )
    .all() as User[];
}
